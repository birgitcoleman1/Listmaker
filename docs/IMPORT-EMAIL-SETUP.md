# Import and email update

## Apply and deploy

1. Back up the database through your normal Supabase process. Apply `supabase/migrations/202611080001_import_mail.sql` in the SQL Editor **once**, after the two existing migrations. It is transactional and additive. It does not remove contacts, import history, emails, categories, or workflows. Do not rerun the initial schema. This migration is not applied by Netlify builds.
2. Add `MAIL_CREDENTIALS_KEY` to Netlify's **Functions / Production** environment. Generate 32 random bytes encoded as base64, for example locally with `openssl rand -base64 32`. Never share or commit the result. Keep it in your secret manager. Changing or losing this key requires re-entering mailbox passwords. Keep the existing `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `POSTMARK_SERVER_TOKEN`, and frontend `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` settings.
3. Merge/deploy the application after the migration succeeds. `npm ci`, `npm test`, `npm run build` are the local checks. Test/build require Node 22. The large SheetJS browser chunk is lazy-loaded when reading an import; no spreadsheet library runs on initial page load.
4. Log in as the mailbox user and choose **Email settings** (on mobile: **More → Email settings**). Enter the actual Migadu mailbox address and its mailbox password. Save, then separately **Verify IMAP & SMTP connection**. Saving alone is not verification. The password is encrypted server-side with AES-256-GCM and never returned to the browser; it is not stored in localStorage. The browser sends it over HTTPS only to the authenticated server function. The encryption key and service role key never enter the frontend. Avoid request-body logging in any external proxy.
5. Activate the domain/mailbox in Migadu if not already done. Netlify Functions must be able to reach `imap.migadu.com:993` and `smtp.migadu.com:465` over TLS. No inbound Postmark webhook or DNS changes are required for this IMAP integration. Workflow emails keep using the existing verified Postmark workspace sender; Migadu SMTP verification does not switch the workflow provider.
6. Choose **Inbox → Sync folder**. Sync each folder as needed. Test with an email sent to your mailbox, create a test folder, move the message, then archive it. Confirm the same changes in Migadu webmail. Test a workflow using your own contact, inspect its Outbox, then refresh that contact's timeline. Use a second user and workspace to confirm restricted mailbox content is absent.

## Import behavior

- `.xls` (BIFF), `.xlsx`, `.csv` supported through SheetJS CE 0.20.3, from its official distribution. First row is headers. Multi-sheet workbooks are reviewed/imported one sheet at a time. 10 MB per file and 5,000 data rows per sheet; oversized files/sheets require splitting. Spreadsheet formulas/macros are not evaluated.
- Mapping ignores case, punctuation and spaces and recognizes common header synonyms. Full-name headers split into first/last name when last name is not separately mapped. All suggested mappings remain editable. Unmapped columns are ignored; existing import history is retained. No export added.
- First name required, email validated when supplied. Validation errors are visible in preview and returned per row. Invalid rows do not prevent valid rows from importing. Exact database constraints remain authoritative.
- User explicitly chooses **skip**, **update**, or **create**. Duplicate email comparison is case-insensitive **within the workspace**. Existing unique-email policy prevents a duplicate email even in create mode (reported as a failed row). Update replaces mapped **non-empty** fields; it does not erase fields with blanks. Company names reuse a case-insensitive workspace match or create a company. No category changes or workflow enrollment occur during import.
- A stable batch UUID makes network retries idempotent, including rows without email. Retry from the existing screen; starting a new upload generates a new batch, and email-less rows are new contacts. Import rows use the batch ID as `source_file` and retain the original filename plus mapped source values in `source_cells`. Summary reports successful, skipped and failed rows with SQL errors. Invalid rows can be corrected in the source and uploaded as a new batch.
- Root cause of `import_records.created_at` was an incorrect generic sort query. Schema stores `imported_at`. `App.load` now uses the real column. No history is deleted, and no unnecessary duplicate timestamp column is introduced.

## Mail privacy and mailbox behavior

- One connection per user per workspace, restricted by both membership and ownership in RLS. Members cannot read another member's mailbox messages, credentials, folders or IMAP locations. Workspace workflow emails remain visible to workspace members, matching the existing shared CRM model. Credentials have no authenticated/anonymous grants or policies, and only server-side service-role operations can use them. Removing workspace membership removes access even if an account record remains.
- Owners/admins/members can configure/sync their own mailbox. Viewers have no mail mutation endpoints, matching existing read-only workspace permissions. Changing an existing connection's email address is intentionally blocked to avoid mixing mailbox histories.
- Sync is **on demand, not push/background**. It reads up to 10 recent messages per request, with **Sync older messages** for earlier mail. A 20-second page-processing budget stops cleanly between messages. Choose **Sync folder** to check new mail and reconcile external moves/deletes; cached folder lists refresh on mailbox operations. At most 10,000 cached locations per folder are reconciled in a request. Very large mailbox reconciliation beyond that is not supported in this release.
- Folders are real IMAP folders. Move and archive are IMAP MOVE (or the protocol library's supported equivalent); archive uses the server's `\Archive` folder, else creates/reuses `Archive`. No messages are permanently deleted by the UI. Mailbox changes also appear in desktop clients/webmail. Folder deletion/rename UI is not included. Cached message content remains in the CRM timeline after moving or removing its remote location; this is app-only historical retention, not a claim that the message still exists in the mailbox.
- Bodies are plain text. HTML-only email is converted to inert text; React never inserts email HTML. Attachments are not stored, downloaded or exposed by this release. Messages over 2 MB show an explicit preview-limit notice and can be read in webmail/desktop clients.
- Contact association is scoped to the account's workspace, using the sender for incoming mail and recipient(s) for outgoing mail, matching the contact's primary or additional email. Multiple matching contacts leave the message unlinked rather than guessing. No new contacts are silently created. Re-sync re-evaluates linkage for fetched messages. Sync older pages if a past message needs reassociation after editing a contact.
- Separate message and IMAP-location records preserve one timeline email across repeated syncs and folder moves. Message-ID identifies copies; messages without it use a source hash (or envelope/size hash for oversized previews). Pathological duplicate Message-IDs or identical oversized no-ID messages can coalesce; these are not a substitute for a provider's globally unique message identifier.
- Workflow messages use the same `email_messages` store as Inbox/timeline, with workflow/job references and one message per job. They are not automatically copied into Migadu's Sent folder because Postmark is the transport. The workflow Outbox is the CRM record, not an IMAP folder.

## Workflow sending/status

- Both the contact card and post-save scan screen call `startContactWorkflow`. The server's existing `manage_enrollment` remains the authority for category selection, permissions, and one active enrollment. The post-scan action only receives the saved contact ID. Enrollment buttons are disabled while busy, and reopening a card reads active enrollment from Supabase.
- Workflow emails now record recipient, subject/body, workflow, job, timestamps, provider ID and errors. The contact timeline merges email records with notes chronologically; workflow-email activity notes are omitted from that display to avoid duplicating the email itself. A timeline refresh does not insert records. Outbox and timeline show at most 200 recent messages per view in this release.
- `queued` means a send is waiting for confirmation. `sent` means Postmark accepted the request (or outbound mail was observed in the connected mailbox). **It is not a delivery receipt.** This update does not configure delivery/bounce webhooks. Newly sent workflow messages are never marked `delivered` without such evidence; use Postmark Activity for delivery confirmation.
- A durable database send claim prevents a workflow job from submitting twice. Network ambiguity is recorded as an explicit failure requiring provider reconciliation. Do **not** reset claims or blindly retry failed/processing email jobs; first check Postmark with the job ID in its metadata. An interrupted process may leave a queued message/processing job requiring owner reconciliation. Exactly-once delivery across an external provider and database is not claimed.
- Existing historical emails still appear in contact timelines. Old records had no reliable workflow/job key; they are not guessed into a workflow Outbox. New workflow messages have explicit links. No existing history is removed.

## Official provider settings

Verified against Migadu's official documentation on November 7, 2026:
- https://www.migadu.com/guides/thunderbird/
- https://www.migadu.com/guides/outlook_android/

Incoming `imap.migadu.com`, port **993**, **SSL/TLS**, normal password. Outgoing `smtp.migadu.com`, port **465**, **SSL/TLS**, normal password with authentication required. Username for both is the **full mailbox email address**. The password is the mailbox password obtained/set through the Migadu mailbox administrator, not the Migadu admin account password or Postmark API token. The accessible client-setup dialog provides these steps without revealing any stored credential.
